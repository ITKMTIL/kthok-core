# กรอบความเป็นนิรนาม (ห้ามละเมิด)

ไฟล์นี้มีสำเนาเหมือนกันทั้งใน kthok-client และ kthok-core แก้ที่หนึ่งต้องแก้อีกที่ให้ตรงกัน

K-Thok ขายความเป็นนิรนาม ทุกฟีเจอร์ ทุกการแก้ ต้องผ่านกรอบนี้ก่อนเสมอ ถ้าขัดกับคำขอ ให้หยุดแล้วถามผู้ใช้ อย่าทำไปก่อน

## สิ่งที่ห้ามเก็บ ห้าม log ห้ามส่งต่อ

- อีเมล, รหัสนักศึกษา, ชื่อจริง, รูปโปรไฟล์ Google → ใช้แค่ตอนยืนยันตัวตนใน `POST /auth/google` แล้วทิ้ง
- นามแฝง → อยู่ใน memory ของห้อง และ localStorage ของผู้ใช้เท่านั้น
- เนื้อหาข้อความ, ข้อความเสียง, คิวเพลง, เกม, ประวัติห้อง, ใครคุยกับใคร → memory เท่านั้น ออกจากห้อง/restart แล้วหาย (ข้อยกเว้นเดียว: ข้อความที่ผู้ใช้เลือกแนบตอนรายงาน ดูตารางด้านล่าง)
- HMAC ของข้อความ (key สุ่มต่อ process) และ contact ของ "อยากคุยต่อ" → memory ไม่เกิน `FOLLOWUP_MS` (10 นาที) หลังห้องจบ contact ส่งถึงอีกฝ่ายเฉพาะเมื่อกดทั้งคู่
- IP address และ user agent → ห้ามผูกกับผู้ใช้หรือเขียนลง DB/log
- เสียงโทร → peer-to-peer ผ่าน WebRTC หรือ TURN ไม่ผ่าน core (`CALL_FORCE_RELAY=true` เพื่อไม่ให้คู่สนทนาเห็น IP กัน)

## สิ่งที่เก็บได้ (Postgres, ไม่บังคับ)

| ตาราง | เก็บอะไร | ทำไม |
| --- | --- | --- |
| `users` | `hash` = HMAC-SHA256(`USER_HASH_SECRET`, รหัสนักศึกษา), คณะ, `banned_until`, `ban_reason`, เวลา | แบนและบล็อกต้องจำคนได้ข้ามครั้ง โดยย้อนกลับเป็นรหัสไม่ได้ |
| `blocks` | คู่ id ของ users | ไม่จับคู่คนที่บล็อกกันอีก |
| `daily_stats` | ยอดรวมรายวัน ต่อคณะ | dashboard admin ไม่มีข้อมูลรายคน |
| `reports` | id ภายในของผู้รายงาน/ผู้ถูกรายงาน, เหตุผล, หลักฐาน (โน้ต + ข้อความที่ผู้รายงานเลือกแนบ) เข้ารหัส AES-256-GCM ด้วย key จาก `SESSION_SECRET`, สถานะ, `expires_at` = 30 วัน | ให้ admin ตรวจ (เจ้าของอนุมัติ 2026-10-03) ลบอัตโนมัติทุกชั่วโมง ข้อความต้องตรง HMAC ของที่ส่งจริงในห้อง |
| `push_subscriptions` | endpoint + key ของ Web Push ที่ผู้ใช้เปิดเอง ผูกกับ users | ส่งแจ้งเตือน (เจ้าของเลือกเก็บใน DB 2026-10-03) ลบเมื่อผู้ใช้ปิด ออกจากระบบ หรือ endpoint ตอบ 404/410 |

- `ban_reason` ห้ามมีข้อมูลระบุตัวตนหรือเนื้อหาแชต
- admin เห็นผู้ถูกรายงานเป็น "ผู้ใช้ #id" + คณะ + ยอดรายงาน/บล็อก ไม่เห็น hash ไม่เห็นว่าใครรายงาน
- payload ของ push มีแค่ `{kind}` (match/message/call/keep) ห้ามใส่เนื้อหา นามแฝง หรือคณะ เพราะผ่าน push service ของ Google/Apple/Mozilla
- ห้ามเพิ่มตาราง/คอลัมน์ที่เก็บเนื้อหา, ความสัมพันธ์ระหว่างคน (นอกจาก block), หรือ timeline รายคน

## สิ่งที่อีกฝ่ายเห็น

นามแฝง + คณะ เท่านั้น (+ contact ที่อีกฝ่ายพิมพ์เองเมื่อกดอยากคุยต่อทั้งคู่) ห้ามส่ง `userHash`, socket id ของ server ภายใน, อีเมล, หรือข้อมูลอื่นไปฝั่งคู่สนทนา

## Session

- token = AES-256-GCM sealed `{v, sub: userHash, faculty, exp}` แก้ไขไม่ได้ อ่านไม่ได้จากฝั่ง client
- คณะมาจากรหัสนักศึกษาหลักที่ 3–4 ผู้ใช้เลือกเองไม่ได้ตอนเปิดล็อกอิน
- ห้ามเปลี่ยน `USER_HASH_SECRET` หลังมีผู้ใช้ (hash เปลี่ยน → แบน/บล็อกหลุด)

## Checklist ก่อนเพิ่มฟีเจอร์

1. ข้อมูลใหม่นี้เก็บที่ไหน นานแค่ไหน? ถ้าไม่ใช่ memory ต้องอธิบายได้ว่าทำไมจำเป็น และระบุตัวคนไม่ได้
2. มีอะไรหลุดไปถึงคู่สนทนาเกินนามแฝง + คณะไหม?
3. server log มีเนื้อหา/ตัวตนไหม? (ห้าม)
4. ไฟล์ที่ผู้ใช้สร้าง (รูปแชร์, เสียง) อยู่ในเครื่องเท่านั้นไหม? server ต้องเป็นแค่ทางผ่าน
5. analytics/third-party ใหม่? ห้ามเพิ่มตัวที่ track รายคน
6. อัปเดต privacy note บนหน้าเว็บ + README ถ้าพฤติกรรมเรื่องข้อมูลเปลี่ยน
7. ฟีเจอร์ที่ต้องการหลักฐาน (เช่น report) ต้องตกลงกับผู้ใช้ก่อนว่าเก็บอะไร เพราะขัดกับ "ไม่เก็บข้อความ"

## ข้อยกเว้นที่ผู้ใช้อนุมัติแล้ว

- admin (ตาม `ADMIN_STUDENT_IDS` ซึ่งเทียบเป็น hash) จับคู่กับบัญชีตัวเองได้เพื่อทดสอบ
- รายงานเก็บข้อความที่ผู้รายงานเลือกแนบ (เข้ารหัส, 30 วัน) — แจ้งไว้ใน privacy note บนหน้าเว็บและในฟอร์มรายงาน
- push subscription เก็บใน DB ผูกกับ hash
- lobby บอกว่าคณะ/หัวข้อไหน "มีคนรอ" แบบไม่มีตัวเลข (กันเดาตัวคนในคณะเล็ก)
- คนที่ถูกบล็อก/รายงานบ่อยถูกหน่วงเวลาจับคู่ (นับจาก DB ไม่มีข้อมูลใหม่)
